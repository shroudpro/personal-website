### 3.3 面试讲述版本

背景：用户的衣物通常分散在照片中，单品信息难以整理和复用。Wardrobe 将照片识别、图像生成和本地衣橱管理放到同一个工作流中。

目标：在不引入数据库、认证系统或独立后端服务的前提下，让个人用户可以导入衣物、审核生成结果、编辑元数据，并进一步组合衣物生成可保存的穿搭图。

行动：项目使用 React 和 Vite 构建界面，由 Vite 插件提供本地 REST API；服务端用视觉模型识别类别、颜色、标签和边界框，用 Sharp 负责图片归一化、裁剪、色键背景清理和透明 PNG 编排；生成接口通过 provider 抽象支持 DashScope 原生接口和 OpenAI 回退。导入与穿搭都设计成可持久化任务，并在每个关键图像阶段等待人工审核。

挑战：图像模型可能生成色键污染、错误细节或不符合预期的构图，同时外部图片接口存在请求格式和限流差异。项目通过边缘去溢色、污染像素校验、本地清理预览、30 秒串行队列和可重新生成的审核状态处理这些问题。

结果：仓库已形成可本地运行的衣橱画廊、三阶段导入审核、上身效果图、自由搭配和 PWA 缓存流程；当前 `npm test` 的 16 项测试通过，项目文档记录了真实 provider 链路与本地文件落盘验证。正式线上部署、完整浏览器回归和个人职责归属仍需补充或确认。

反思：如果继续推进，应先把当前 Vite 开发期 API 拆成可部署服务，补充持久化、密钥管理和端到端浏览器测试，同时用真实样本评估识别、裁剪和生成质量，而不是只依赖结构化测试。

## Challenges & Solutions

- 挑战：衣物照片可能包含人物、其他衣物和复杂背景。解决：先用结构化视觉识别获取每件衣物的类别、元数据和边界框，再逐阶段审核裁剪结果。
- 挑战：生成衣物图的色键背景可能污染透明边缘。解决：用 Sharp 做色差判断、羽化、去溢色、透明画布重排和污染像素验证，并提供不重新调用模型的本地清理预览。

## 6. 可复用经验库

### 技术决策

- 决策：采用本地优先的 JSON/PNG 存储，而不是引入数据库和认证系统。
- 背景：项目定位是个人衣橱，仓库需要保留原图、生成图和任务中间结果的本地隐私边界。
- 取舍：减少部署组件和数据外泄面，但牺牲了多用户、云端同步和正式生产部署能力。
- 可迁移经验：个人工具或隐私敏感的单用户原型可以先把数据边界做清楚，再在需求明确后补充服务端持久化。

- 决策：使用 `crop`、`garment`、`modeled` 三阶段审核，而不是一次生成后直接入库。
- 背景：识别边界框、透明衣物图和上身效果图的质量问题不同，用户需要在每一步看到结果。
- 取舍：流程更长、需要用户参与，但每一步都能拒绝或重新生成，降低错误数据进入衣橱的风险。
- 可迁移经验：涉及生成式模型的产品，应把可验证的中间产物和人工批准设计成一等状态。

- 决策：通过 provider 抽象同时支持 DashScope 和 OpenAI 图片生成。
- 背景：当前开发测试使用 DashScope 原生接口，同时保留 OpenAI 图片编辑链路作为回退或切换选项。
- 取舍：增加配置和测试成本，但避免业务逻辑绑定单一服务的请求格式。
- 可迁移经验：对外部服务做小型适配层，优先统一输入、输出和错误语义，而不是在业务代码中散落 provider 分支。

### 问题解决

- 问题：生成的色键背景可能在衣物边缘留下污染。
- 定位过程：服务端对 RGBA 像素计算与色键的距离，统计污染像素和最大溢色，并把失败的原始衣物图保留下来供复核。
- 解决方案：实现色差阈值、羽化、去溢色、透明画布重排和可调清理容差；前端提供清理预览和接受入口。
- 最终结果：衣物图可以在本地处理为透明 PNG；如果自动清理失败，用户可以调整参数而无需重新调用图片模型。

- 问题：DashScope 原生图片生成接口与 OpenAI 图片编辑接口的请求结构不同，并有调用间隔限制。
- 定位过程：将接口请求、参考图编码、响应图片地址解析、临时图片下载和错误响应分开测试。
- 解决方案：增加 `createDashScopeImageProvider` 与 `createImageGenerator`，在 provider 内串行排队并使用最小间隔。
- 最终结果：测试覆盖了原生请求字段、临时图片下载、串行开始时间和中文错误信息，同时保留 OpenAI provider 路径。

- 问题：生成任务耗时较长，服务重启后不能依赖内存状态继续处理。
- 定位过程：将任务的阶段、尝试次数、错误、资产地址和更新时间写入本地 `job.json`，启动时扫描任务目录。
- 解决方案：导入和穿搭分别持久化状态，并在服务启动时把 pending、queued 或 processing 任务恢复到可继续执行的状态。
- 最终结果：任务结果可以在页面轮询显示，服务重启后具备继续处理未完成任务的代码路径；完整重启场景仍待浏览器和真实环境复测。

### 工程方法

- 使用了什么方法：先通过结构化模型输出建立明确的衣物元数据和边界框，再分阶段生成、审核和持久化。
- 为什么有效：每个阶段都有可见资产、明确状态和单独的失败处理，便于定位是识别、图像生成还是本地处理出了问题。
- 适合什么场景：适合外部模型不稳定、结果需要人工判断、且中间结果具有复用价值的工作流。

- 使用了什么方法：用测试替身注入 `fetch`、时间函数和睡眠函数，测试 provider 的请求和限流行为。
- 为什么有效：不需要真实 API Key 就能验证请求体、错误映射和并发顺序，降低测试成本并避免泄露凭据。
- 适合什么场景：适合有外部 HTTP 服务、速率限制或异步队列的 Node 服务模块。

- 使用了什么方法：把真实运行数据放入被 Git 忽略的 `data/`，把环境变量和个人参考图留在本地。
- 为什么有效：源代码和配置模板可以公开，而个人衣物、生成图片和凭据不进入仓库历史。
- 适合什么场景：适合个人资料、图片资产或本地实验数据不应被提交到公共仓库的项目。

### 失败或不足

- 哪些地方没有完成：项目材料未确认正式线上部署，也没有可确认的 Demo 地址、用户数量或业务结果。
- 哪些方案存在局限：当前导入 API 依托 Vite 开发期插件；`npm run build` 只生成静态文件，不能单独提供导入服务。

- 哪些地方没有完成：全新上传图片的识别与裁剪、多个浏览器断点、服务重启恢复和部分真实浏览器交互在 `项目状态.md` 中仍列为待验证。

## 8. 可用于面试的追问与回答素材

- 问：为什么选择本地优先方案？答：项目定位是个人衣橱，文档明确把衣物记录、原图、生成图和任务中间结果放在本地 `data/`，并避免数据库、认证和独立后端服务。这样降低了部署和隐私暴露面，但也意味着正式上线前必须补充持久化、密钥管理和多用户能力。
- 问：项目中最难的问题是什么？答：一个难点是生成衣物图的色键背景会污染透明边缘。实现中用 Sharp 做色差判断、羽化、去溢色、透明画布重排和污染像素验证，并在失败时保留原图、允许本地调节容差和预览，避免每次都重新调用模型。
- 问：为什么要做三阶段审核？答：裁剪边界、衣物净图和上身效果图的错误类型不同。分别审核可以在错误进入本地衣橱前停止流程，同时允许对衣物图和上身图附加方向重新生成。
- 问：你具体负责了哪些部分？答：仓库能确认的只是模块实现，不能据此确认个人职责；Git 历史提交作者显示为 `Thijs`，当前工作区还包含未提交改动。需要先确认本人负责范围，再从 React 界面、图片处理、provider、任务 API和测试中选择准确表述。
- 问：如果重新做一次，你会如何改进？答：会把 Vite 开发期 API 拆成可部署后端，加入正式持久化和密钥管理；同时补充全新图片导入、浏览器断点、服务重启和真实生成质量的端到端测试，并为生成任务增加可观测性。
